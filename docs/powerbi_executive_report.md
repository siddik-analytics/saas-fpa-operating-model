# The Power BI executive report

**Phase 10.** `powerbi/Helio_Executive_Report.pbip` — the executive reporting interface over the
Phase 3–8 analytical stack. A Power BI Project (PBIP): a TMDL semantic model and a PBIR report
definition, both plain text and both committed. Generated by `src/build_powerbi.py`; validated
statically by `src/validate_powerbi.py` and `tests/test_powerbi_report.py`.

No `.pbix` binary. No embedded data. No machine-specific path. No cloud dependency, no gateway
and no workspace: the model reads the committed CSV marts off disk through one parameter.

**Status: accepted in Power BI Desktop.** The project opens, the semantic model refreshes across
all 27 tables, and the five report pages render and have been inspected visually — the captures in
[`docs/assets/powerbi/`](assets/powerbi/) come from that build. Getting there took five rounds of
defects, none of them analytical, each found further into Desktop than the last:

| # | Where Desktop stopped | Error | Fixed |
|---|---|---|---|
| 1 | PBIR report loading | *Cannot find file 'version.json'* / *Error Reading StorageSection: ReportDocument* | Section 12 |
| 2 | Model creation — measure metadata | *…has both FormatString property and FormatStringDefinition property defined* (`PFE_TM_MEASURE_FORMAT_STRING_DEFINITION_CONFLICT`) | Section 13 |
| 3 | Model creation — object namespace | *The 'Ending ARR' measure cannot be created because a column with the same name already exists* (`PFE_XL_MEASURE_COLUMN_ALREADY_EXIST`) | Section 14 |
| 4 | Report pages | **No error.** The model opened and refreshed; no page appeared, and Desktop replaced the report with a blank one | Section 15 |
| 5 | Number formatting | **Not a failure to open.** The project opened, refreshed and rendered; some labels read `$0.0M` for figures that were not zero | Section 16 |

**The project now opens, refreshes and renders in Desktop, and the layout reads as designed.**
What remains is a confirming pass over the number formatting corrected in section 16.

Nothing in the expected results, the marts, the SQL or the Excel workbook has changed through any
of the four rounds, and no reported number has moved. What changed is how the project is written
to disk: which files exist, how a format is declared, what the objects are named, and which
version Desktop is told to read them as.

**Python cannot open Power BI Desktop.** That is the lesson every round teaches, and each defect
was invisible to the checks that existed at the time — the fourth was invisible to Microsoft's
validator too and produced no error at all, and the fifth produced correct numbers that simply
could not be read. The count is now 503 and includes a scaffold family, a measure-format family, a
table-namespace family, a report-pages family and a presentation family (section 10), each with
mutation tests behind it. None of that was a substitute for opening the file: every one of the
five defects reached Desktop with the static checks passing. Section 11 records the manual
acceptance, which is what actually established that the report works.

## 1. Purpose and audience

The Excel workbook (Phase 9) is the financial-management interface: it shows the working. This
report is the **executive** interface: five pages, six analytical visuals each, every title a
conclusion rather than a label, answering the reporting cycle's questions in the order a board
asks them.

- Where does FY2026 land against the Board Budget, and can we fund it?
- Is the recurring base healthy, and what is at risk in the next four quarters?
- Why does sales capacity not equal achievable bookings?
- What do the P&L and the cost base actually do?
- Is the hiring case affordable, and separately, is it attractive?

It is not a second forecast engine and not a self-service data model. Every business calculation
was already made and controlled in `sql/`; the semantic model reads those results, and DAX does
presentation arithmetic over them.

## 2. Why a PBIP project and not a .pbix

A `.pbix` is a binary. Committed to a public repository it is an opaque blob: a reviewer cannot
see a measure, a relationship or a visual without installing Power BI Desktop and opening it, and
a diff shows nothing but "binary files differ".

A **Power BI Project** stores the same content as text — TMDL for the semantic model, PBIR JSON
for the report. Every measure, every Power Query step, every relationship and every visual is
reviewable in a pull request. That is the whole reason for the format choice here, and it is why
the project is *generated* rather than hand-authored: the generator is the specification, and
`src/validate_powerbi.py` re-runs it and fails the build if the committed files have drifted.

The trade-off is real, and it has cost four acceptance attempts: generating a project means the
PBIR and TMDL formats have to be got exactly right without Desktop to check the work, and
sections 12 to 15 are what that looked like. The mitigations are Microsoft's own PBIR validator
in the loop (section 11) and four check families asserted on every build (section 10) — though
the fourth failure passed both the schema and Microsoft's validator, so the honest position is
unchanged: a generated project is only proven when Desktop opens it.

## 3. Architecture

```text
powerbi/
  Helio_Executive_Report.pbip                  project file
  Helio_Executive_Report.SemanticModel/
    definition.pbism
    definition/
      model.tmdl, database.tmdl, relationships.tmdl, expressions.tmdl
      tables/*.tmdl                            27 tables
  Helio_Executive_Report.Report/
    .platform
    definition.pbir                            version 4.0 - decides whether Desktop reads pages
    definition/version.json                    report definition version - Desktop reads it first
    definition/report.json
    definition/pages/pages.json
    definition/pages/<page>/page.json
    definition/pages/<page>/visuals/<visual>/visual.json
    StaticResources/RegisteredResources/HelioExecutive.json      our theme
    StaticResources/SharedResources/BaseThemes/Fluent2-CY26SU08.json   the base it sits on
  measures.md                                  generated measure library
  validation/
    dax_validation_queries.dax                 the queries a reviewer runs in Desktop
    expected_measure_results.csv               the answers, generated from the marts
```

**27 tables**: three dimensions (`Date`, `Segment`, `Scenario`) and 24 fact tables, one per
committed mart. **108 measures** (104 visible, 4 hidden supporting). **27 relationships**, every
one single-direction and many-to-one. **Five pages, 45 visuals** — 30 analytical, the rest
headers, slicers and panel labels.

Lineage tags are `uuid5` over a fixed namespace rather than random, so a rebuild produces a
byte-identical project. A no-op regeneration leaves an empty diff, which is what makes drift
detection meaningful.

## 5. The semantic model

### Dimensions

The three dimensions are the only tables not sourced from a mart. Each is built in Power Query
from a literal list, so the model carries its own conformed dimensions rather than inferring them
from whichever fact happens to load first.

`Date` is a **daily, contiguous** calendar spanning 2023-12-01 to 2027-12-31 — daily and contiguous
because that is what lets it be marked as the model's date table (`dataCategory: Time`). It carries
Year, Fiscal Year, Month Number, Month, Month Sort, Quarter Number, Quarter, Fiscal Quarter,
Quarter Sort, and — the column that does the real work — **Period Type**, which is `Actual` on or
before the 2026-06-30 cutover and `Forecast` after it. The actual/forecast split every page shows
is that one column, defined once. Every fact joins on its month-end day.

`Segment` holds the three members (SMB, Mid-Market, Enterprise) with a sort column so they read
smallest-to-largest rather than alphabetically. `Scenario` holds Bear, Base, Bull, sorted the same
deliberate way.

Facts filter *from* the dimension, many-to-one, single-direction. There is no bi-directional
filter and no many-to-many relationship anywhere in this model.

### The eight disconnected tables

Where a star join would be wrong, the table is left disconnected and the reason is recorded in
`DISCONNECTED_NOTES` in `src/powerbi_tables.py`, asserted by tests so a later edit cannot quietly
connect one:

| Table | Why not joined |
|---|---|
| Runway Policy | Its five paths span three operating scenarios **and** two hiring cases. A three-member Scenario dimension cannot represent that; joining would strand the hiring rows on a blank member. |
| Management Variance | Every row is already a stated FY2026 or Dec-2026 comparison. A Date join would let a month filter blank the Board scorecard. |
| Commentary | Nine deterministic rows, no date or segment grain. |
| Operating Income Bridge | One Budget-to-Base walk for FY2026, not a time series. |
| Cohort ARR | Grain is cohort *age* in quarters, not calendar time. Segment only. |
| Unit Economics | CAC uses a one-quarter spend lag, so its grain is its own fiscal quarter. Segment only. |
| CRM Opportunities | Win rate and median cycle are all-time figures. Segment only. |
| New Logo Diagnosis | An H2 2026 summary, not a monthly series. Segment only. |

Adding a bridge table to force these onto the calendar would have produced numbers that respond to
a month slicer and mean nothing. Leaving them disconnected means a date filter cannot change them,
which is correct.

### Naming: the ` Source` convention

Columns, measures and hierarchies in one table share a single case-insensitive namespace, so a
measure cannot take a name a column already holds. Twenty-three did, and section 14 is what
happened. The convention that resolves it, applied throughout:

| | |
|---|---|
| **The measure keeps the business name** | `Ending ARR`, `Ending Headcount`, `Policy Runway Months` |
| **The stored column takes a ` Source` suffix and stays hidden** | `Ending ARR Source` |
| **`sourceColumn` is untouched** | still `Ending ARR`, the Power Query output |
| **The mart is untouched** | still `fct_arr_forecast.ending_arr` |

So the field list shows the business name on the measure, the technical column behind it is
hidden, and no mart, CSV, SQL model or Power Query step was renamed to achieve it. The suffix
appears only where a measure claims the name — 23 columns — and the validator fails if it ever
appears anywhere else, or on a column that is not hidden.

### Filtering on the way in

Two Power Query filters matter for correctness. `Segment <> "Total"` drops the marts' own
pre-aggregated Total rows so the three segments sum to the company figure instead of double
counting it; `path = "Base"` on the ARR forecast keeps the model on the reforecast path. Both are
visible in the table's TMDL partition.

## 6. Measure design

Three rules, stated in full at the top of [`powerbi/measures.md`](../powerbi/measures.md) and
enforced by the validator:

**1. SQL owns the business logic.** Movement classification, the TTM cohort and its per-customer
GRR cap, available-to-renew, ramp and capacity, `LEAST(capacity, pipeline)`, every driver, the
bottom-up P&L, the Board-policy runway, the computed hire counts, every bridge, materiality,
polarity and the commentary text are all produced upstream. A measure either reads a stored value
or forms a presentation ratio over stored values.

**2. A ratio is a ratio of aggregates, never an average of ratios.** NRR, GRR, logo retention,
gross margin, attainment, CAC, CAC payback and cohort retention all divide a summed numerator by a
summed denominator. `AVERAGE` appears nowhere in the model and `src/validate_powerbi.py` fails the
build if it ever does. This is not pedantry: averaging the three segment NRRs at 30 June 2026 gives
98.1%, while the correct ARR-weighted ratio of aggregates gives 101.8%. One of those numbers would
have been wrong on a board page.

**3. A measure with no defined value returns BLANK.** TTM retention is measured at a point in time;
the two sales-efficiency metrics are quarterly. Asked across several periods they return blank
rather than a plausible-looking number that means nothing. `Ending ARR` is semi-additive — a year
returns its final month, never a sum of twelve.

### Number formats: one mechanism per measure

A measure carries **either** a static `formatString` **or** a dynamic `formatStringDefinition`,
never both — Power BI Desktop rejects the whole model if it finds the pair, which is what section
13 is about. The rule that decides which:

| | |
|---|---|
| **One stable unit** — ARR, revenue, gross profit, operating income, CAC, percentages, headcount, runway months | **Static.** 103 of the 108 measures. |
| **Unit varies by row** — the generic Budget-vs-Base scorecard measures (USD, basis points, FTE on one grain) and the scenario driver value (rates, dollars per month, multipliers, months) | **Dynamic**, a `SWITCH` over the row's own `Unit` column. 4 measures. |
| **Returns text** — `Board Floor Status` | **Neither.** 1 measure. |

Dynamic formatting is not used anywhere a static format would do. Where it is used, the measure
stays numeric: `FORMAT()` is deliberately never called inside an expression to avoid the model
metadata, because that returns text and breaks sorting, aggregation and chart behaviour.

## 7. Opening the project

1. Install Power BI Desktop and enable **File > Options > Preview features > Power BI Project
   (.pbip) save option**.
2. Open `powerbi/Helio_Executive_Report.pbip`.
3. Set the **RepoRoot** parameter to your clone path — *Transform data > Manage parameters* —
   then **Refresh**.

The committed `RepoRoot` default is deliberately **empty**. A Power BI parameter default is stored
in the file, and an absolute path from the author's machine has no business in a public repository;
`src/validate_powerbi.py` fails the build if a drive letter or a `/Users/` path appears anywhere in
the project. To stamp your own clone path instead of setting it in the UI:

```bash
python -m src.build_powerbi --repo-root auto
```

Every table then reads `RepoRoot & "/data/marts/<mart>.csv"`. There is exactly one parameter and
one source pattern, so a clone is one edit away from refreshing.

**After a Desktop session, regenerate before committing.** Desktop writes into a project it opens:
per-user state under `.pbi/`, a model `diagramLayout.json`, and — once you set the parameter —
your own absolute path stamped into `expressions.tmdl`. It also normalises the TMDL it saves.
`.gitignore` covers the local files and two checks fail the build if any of them reach the
repository, but the reliable move is `python -m src.build_powerbi`, which restores the empty
`RepoRoot` and the canonical project. Desktop's save is not the source of truth; the generator
is.

## 8. Formatting

One corporate blue plus neutral greys, per PHASE1_SPEC section 12. Red and green are reserved
exclusively for unfavourable and favourable variance and appear nowhere decoratively.

The theme is a registered resource, `HelioExecutive.json`, so a colour is defined once rather than
set on each visual.

| Role | Hex |
|---|---|
| Series 1–8 (`dataColors`, in order) | `#2E5FA3` `#7FA3D1` `#1F3864` `#9CA3AF` `#C98A1B` `#4C7CBF` `#B9C7DA` `#6B7280` |
| Favourable (`good`) | `#1E7B4D` |
| Unfavourable (`bad`) | `#B23A2E` |
| Neutral | `#9CA3AF` |
| Foreground / visual background | `#1F2937` / `#FFFFFF` |
| Page canvas and outspace | `#F7F8FA` |
| Rule | `#E5E7EB` |

Green and red appear only as `good` and `bad` — they are not in the series palette at all, so a
chart cannot pick one up by accident for an ordinary category. The series list is five blues, two
greys and one amber, which is what keeps a variance colour meaningful when it does appear — on the
waterfalls, where a bar is coloured by its actual effect, and on the favourability columns.

No pies, no gauges, no gradients, no 3D. A 1280×720 canvas. Number formats are declared once per
measure in the model, so a figure carries the same format wherever it appears — no visual
overrides a display unit or a decimal place. **Section 16** covers how each measure's unit and
scale were chosen, and why a dollar figure is sometimes shown in thousands rather than millions.

## 9. Traceability

Every number on every page resolves backwards through a chain that is entirely inspectable:

```text
visual.json          which measure, in which filter context
  -> measures.md     the DAX, the source mart and fields, the equivalent SQL
    -> the mart      data/marts/<mart>.csv, regenerated by the build
      -> sql/        the model that produced it, under manifest.yml
        -> controls  ctl_arr_reconciliation and its five siblings
```

`measures.md` is generated from `src/powerbi_model.py`, `src/powerbi_tables_*.py` and
`src/powerbi_pages.py` by `python -m src.powerbi_docs`, and the test suite regenerates it on every
run and fails if the committed copy has drifted. **Documented DAX and shipped DAX cannot diverge.**
Each measure entry names its home table, format, display folder, source mart and fields, the SQL
that produces the same number, its filter-context behaviour, and which visuals read it.

## 12. The first Desktop acceptance attempt, and what it changed

Recorded in full rather than quietly fixed, because the interesting part is not the bug — it is
that 409 automated checks reported the project healthy while Power BI Desktop could not read it.

### What happened

Power BI Desktop (August 2026, 2.157.879.0) refused to open
`powerbi/Helio_Executive_Report.pbip`:

```text
Cannot find file 'version.json'
Error Reading StorageSection: ReportDocument
```

### Root cause

`Report/definition/version.json` was never generated. It carries the report definition version
and Desktop reads it before anything else, so the load aborted at the first missing file.

Desktop stops at its first failure, so that one message understated the problem. Validating the
project against Microsoft's PBIR validator found **65 errors and 6 warnings**, of which the
missing `version.json` was one:

| Diagnostic | Count | What was wrong |
|---|---|---|
| `PBIR_FORMATTING_OBJECT_UNKNOWN` | 54 | `title`, `background` and `border` were written into `visual.objects`. They are **container** formatting objects and belong in `visual.visualContainerObjects` |

All fixes are in the generator — `src/build_powerbi.py`, `src/powerbi_report.py` and the page

The scaffold contract is now declared once, as `REPORT_SCAFFOLD` and `MODEL_SCAFFOLD` in

the generator and the validator cannot drift, and a file that stops being written fails the
build instead of reaching Desktop.

### Why the automated checks missed it

The 409 checks tested the project against **its own specification**, thoroughly. Nothing tested
it against **Power BI's** requirements: there was no check that the scaffold was complete, so a
file the generator never wrote was invisible to a validator that only knew about files the
generator did write. The scaffold family (section 10) and the Microsoft CLI in the build loop
(section 11) are the two answers to that, and the mutation tests exist so neither can rot.

Nothing in the semantic model, the DAX, the expected results, the marts or the Excel workbook
was touched. The defect was serialisation, and the fix stayed there.

## 13. The second Desktop acceptance attempt — a model-layer defect

The scaffold fixes in section 12 worked: Desktop read the PBIR report and moved on to building
the semantic model. It then rejected the model:

```text
The Measure 'Management Variance'['Budget'] has both FormatString property and
FormatStringDefinition property defined which is not supported scenario.
PFE_TM_MEASURE_FORMAT_STRING_DEFINITION_CONFLICT
```

### Root cause

A measure may carry a **static** format string (`formatString`) or a **dynamic** one
(`formatStringDefinition`, a DAX expression evaluated per cell), but never both. Four measures
carried both, and Desktop rejects the entire model rather than the offending measure.

Desktop stops at the first, so the error named only one. The full inventory:

| Measure | Static format it carried | Dynamic format it carried |
|---|---|---|
| `Management Variance[Budget]` | `$#,##0.0,,"M"` | `SWITCH` on `[Unit]` |
| `Management Variance[Base Reforecast]` | `$#,##0.0,,"M"` | `SWITCH` on `[Unit]` |
| `Management Variance[Variance vs Budget]` | `+$#,##0.0,,"M"` | `SWITCH` on `[Unit]` |
| `Forecast Drivers[Driver Value]` | `0.00` | `SWITCH` on `[Unit]` |

Across all 108 measures: **103 static only, 0 dynamic only, 4 both, 1 neither.**

### Which mechanism each measure should use

Dynamic format strings are not a stylistic choice here — for these four they are the correct
answer, and the static property is the one that had to go:

- **The Management Variance measures** are deliberately generic. One measure reads the Budget
  column for whatever metric is in context, and that metric set mixes units: nine USD rows, one
  basis-point row (the gross-margin walk) and one FTE row (headcount). The static format they
  carried would have printed a dollar sign in millions on the basis-point row and on the
  headcount row. That is exactly the defect dynamic formatting exists to prevent.
- **`Forecast Drivers[Driver Value]`** reads one stored driver value across rates, dollars per
  month, multipliers and months. A single static format cannot serve four units.

Everything else — ARR, revenue, gross profit, operating income, CAC, percentages, headcount,
runway months — has one stable unit and keeps a **static** format string. No dynamic format was
introduced where a static one suffices.

Two details worth recording, because dropping the static property could have cost presentation
quietly:

1. `Variance vs Budget` is a variance and its static format carried a leading `+` that the shared
   dynamic `SWITCH` did not. It now has its own signed variant (`MV_FORMAT_SIGNED`), so a
   positive variance still reads `+$1.2M` rather than `$1.2M`.
2. `Forecast Drivers` carries a `months` unit that the `SWITCH` did not name, so those three rows
   fell to the numeric fallback and rendered unlabelled. A `months` branch was added while the
   expression was open.

The measures stay **numeric**. `FORMAT()` was deliberately not used inside any expression to
sidestep the model metadata: that would return text and break sorting, aggregation and chart
behaviour.

### The invariant, enforced in code

`Measure.__post_init__` in `src/powerbi_model.py` now refuses the combination outright, so a
conflicting measure cannot be declared — the specification fails to import rather than emitting
TMDL that Desktop will reject. `measure_tmdl` in `src/build_powerbi.py` refuses to serialise it
as a second line of defence, and `check_measure_formats` in `src/validate_powerbi.py` parses the
**written TMDL** back and checks it independently of both, because the emitted file is what
Desktop actually opens.

Three tests make each of those guards fail on demand.

### On the Desktop reference

Section 12 used a Desktop-saved project as the authority for PBIR schema versions. **That
authority does not extend to TMDL.** The reference is a `.pbix`, which stores its model as a
binary Analysis Services backup, not TMDL — and being a blank report it contains no measures at
all, so it could not have shown a format-string declaration either way. No offline TMDL
validator was available: neither the .NET SDK nor `pbi-tools` is installed on this machine, and
Microsoft's PBIR CLI validates the report, not the semantic model.

What the failure does establish is that Desktop parsed `formatStringDefinition` correctly — it
identified the property by name and objected only to the pairing. The property syntax is
therefore confirmed by Desktop itself; it was the combination that was wrong.

### Other model metadata, swept

Since Desktop had advanced into TOM, the rest of the model metadata was checked for mutually
exclusive or invalid combinations rather than assuming this was the last one. No further
conflicts were found:

| Checked | Result |
|---|---|
| Duplicate property lines within any measure, column or partition block | none |
| `sortByColumn` targets | all resolve to a real column in the same table; none self-referential |
| `formatString` on non-numeric columns | none |
| String columns with an aggregating `summarizeBy` | none |
| Hidden key columns | none |
| Table `dataCategory` | only `Date`, `Time`, with exactly one key column |
| Partitions per table | exactly one each |
| Relationship names | 27, all unique, all single-direction many-to-one |
| Lineage tags | 302, all unique |
| `compatibilityLevel` | 1601 — dynamic format strings are supported well below this |

This is a sweep, not a proof. Desktop may still object to something at a later stage of model
creation or at first refresh, and the honest position stays the one in section 11.

## 14. The third Desktop acceptance attempt — a namespace collision

The format fixes in section 13 worked: Desktop began creating model objects. It then refused one:

```text
The 'Ending ARR' measure cannot be created because a column with the same name already exists.
PFE_XL_MEASURE_COLUMN_ALREADY_EXIST
```

### Root cause

Columns, measures and hierarchies in one table share a **single, case-insensitive namespace**.
A measure cannot take a name a column in the same table already holds. `ARR Forecast` held both a
stored column `Ending ARR` (sourceColumn `Ending ARR`, from `fct_arr_forecast.ending_arr`) and a
measure `Ending ARR` reading it.

Desktop stops at the first invalid object, so it named one of **23**:

| Table | Colliding names |
|---|---|
| ARR Forecast | Beginning ARR, New Logo ARR, Expansion ARR, Reactivation ARR, Contraction ARR, Churn ARR, Ending ARR |
| Retention | Cohort Customers, Cohort Beginning ARR |
| GTM Constraint | New Logo Capacity, Constrained New Logo ARR |
| Sales Capacity | Expected Attainment, Actual Bookings |
| New Logo Diagnosis | Budget New Logo ARR |
| Headcount | Beginning Headcount, Hires, Departures, Ending Headcount |
| Scenario Monthly | Scenario Operating Income, Scenario Ending Cash |
| Runway Policy | Policy Avg Monthly Burn, Policy Runway Months, Board Floor Months |

The model has no hierarchies, so column↔hierarchy collisions were structurally impossible; no
duplicate measure name existed within a table; and no measure name was duplicated across the
model. All 23 were column↔measure.

### The convention

**The measure keeps the business name. The stored column takes a ` Source` suffix.**

```text
measure      Ending ARR                    <- what the field list shows
column       Ending ARR Source             <- hidden, exists only to be summed
sourceColumn Ending ARR                    <- unchanged: the Power Query output name
mart column  fct_arr_forecast.ending_arr   <- unchanged
```

TMDL lets the semantic-model column name differ from `sourceColumn`, so the rename is confined to
the semantic model. **No mart, no CSV, no SQL model and no Power Query step was renamed.** A test
asserts that `fct_arr_forecast.csv` still carries `ending_arr` and no ` Source` column.

`Ending ARR`, `New Logo ARR`, `Revenue`, `Gross Profit`, `Operating Income`, `Ending Headcount`,
`Policy Runway Months` and the rest keep the names a reader looks for. Renaming the measures
instead — `Ending ARR Measure`, or moving everything to a disconnected Measures table — would have
cost exactly the clarity the report exists to provide. A Measures table was considered and
rejected: it is an architecture change, and this was a naming defect.

### What the rename touched

All 23 colliding columns were **already hidden**, none was used as a sort-by column, a
relationship key, or a field on any visual, and no measure in another table referenced one. The
blast radius was therefore 23 column declarations and 31 DAX column references, all inside their
own table's measures. Three ratio-discipline checks in `src/validate_powerbi.py` that assert the
stored-column names by string were updated to match.

The ` Source` columns stay hidden. Visible columns are the ones visuals legitimately need — dates,
segments, scenarios, line items, metric labels, period labels — and those were never in
collision, because nothing is trying to be both an axis and an aggregate.

### One thing the fix revealed

`unused_measures()` — the check enforcing PHASE1_SPEC's restraint rule, that every measure is read
by a visual or by a measure that is — had been passing on a false positive. It matches
`[Measure Name]` in DAX text, and a fully-qualified **column** reference like
`'Sales Capacity'[Actual Bookings]` matched too. Once the columns were renamed, two measures were
exposed as genuinely unread: `Sales Capacity[Actual Bookings]` and
`Scenario Monthly[Scenario Ending Cash]`.

Both were resolved by having the measures that duplicated their aggregation call them instead:

- `Actual Attainment` summed `'Sales Capacity'[Actual Bookings Source]`, which is *literally* the
  definition of `[Actual Bookings]`. Textually identical substitution.
- `Scenario Dec-27 Cash` summed `'Scenario Monthly'[Scenario Ending Cash Source]` under a
  Dec-2027 filter. `[Scenario Ending Cash]` is that sum under `LASTNONBLANK`; the mart holds
  exactly one row per scenario at 2027-12-31 and it is each scenario's last month, so the two
  return the same value. Verified against the mart rather than reasoned about.

No arithmetic changed and no reported number moved. An aggregation is now defined once instead of
twice, which is the state the collision had been hiding.

### The guards

- `Table.__post_init__` in `src/powerbi_model.py` refuses a colliding declaration, case-insensitively.
- `check_table_namespace` in `src/validate_powerbi.py` rebuilds the namespace from the **emitted
  TMDL** — columns, measures and hierarchies — and fails on any collision, any duplicate measure
  within a table, and any measure name duplicated across the model. It also asserts that every
  ` Source` column is hidden and that the suffix is never used where no measure claims the name,
  so the convention cannot spread into columns that never needed it.
- A test walks every DAX column reference and fails on one that resolves to no column, so a
  rename cannot silently leave a measure pointing at a name that no longer exists.
- Four mutation tests: a colliding declaration, a collision that differs only in case, a
  ` Source` column renamed back in the emitted TMDL, and a duplicated measure name.

## 15. The fourth Desktop acceptance attempt — the pages that were never read

The namespace fixes in section 14 worked. Desktop **opened the project and refreshed the
semantic model successfully** — 27 tables, all loading. Then it showed **no report pages at all**,
replaced the report with a blank single-page one of its own, and saved over it. Five pages and 45
visuals were discarded without a single error message.

This is the subtlest of the four failures and the only one that produced no error to read.

### Root cause

`definition.pbir` carries a `version` that tells Desktop **which report-definition format to
read**. It said `"1.0"`. Desktop writes `"4.0"`.

At `"1.0"` Desktop does not look in `definition/pages/` at all. The pages were not rejected — they
were never read. Finding a report definition it considered empty, Desktop did what it does with an
empty report: it created `Page 1` and wrote the project back to disk.

```json
"version": "1.0"     ← what shipped: schema-valid, silently ignored
"version": "4.0"     ← what Desktop writes
```

**Nothing could have caught this.** `definitionProperties` types `version` as a free-form string,
so the published schema accepts any value. Microsoft's own PBIR validator passed the project.
Every check in this repository confirmed the five page folders, their `page.json` files and all 45
`visual.json` files existed exactly where they should — because they did. The one thing nothing
checked was whether the values Desktop *reads* matched the values Desktop *writes*.

Worse, the defect was self-inflicted and recent. The generator originally emitted `"4.0"`. It was
changed to `"1.0"` during the section 12 work, reasoning from the schema — which types the field
as a string and therefore constrains nothing — rather than from evidence. That is exactly the kind
of guess sections 12 and 13 were written to warn against, made while writing them.

### The scaffold, at last

Desktop overwriting the report had one redeeming consequence: it left behind a **complete,
Desktop-authored PBIP** — the ground truth the first three rounds worked without. Sections 12 and
13 had to make do with a `.pbix`, which carries no `.pbir`, no `.pbism` and no TMDL.

Comparing it against the generator settled several open questions at once:

| File | Desktop | Ours | Verdict |
|---|---|---|---|
| `definition.pbir` `version` | `4.0` | `1.0` | **the defect** |
| `definition.pbir` `$schema` | absent | present | kept — `definitionProperties` marks it required and Fabric rejects a definition file without one |
| `definition/version.json` | `2.0.0` | `2.0.0` | confirmed |
| `page.json` schema and shape | `page/2.1.0` | `page/2.1.0` | confirmed |
| `.platform`, `.pbism`, `.pbip` | — | — | byte-identical, `logicalId` included |
| `report.json` `themeCollection` | `baseTheme` | `customTheme` only | **fixed — see below** |
| `database.tmdl` `compatibilityLevel` | `1606` | `1601` | adopted Desktop's |
| Table TMDL | Desktop's own | ours | **accepted verbatim; only defaults dropped** |

The last row matters. Desktop rewrote all 27 table files, and the only changes were its own
normalisations: it dropped `crossFilteringBehavior: oneDirection` (the default), unquoted
identifiers it considers bare-safe, and added a trailing newline. **No measure, column, format
string, relationship or partition was altered.** The TMDL this project generates is the TMDL
Desktop writes — which is what section 13 could not establish at the time.

### The missing base theme

Desktop packages a base theme with every report, and the schema describes a custom theme as one
"applied on top of the base theme", with undefined properties falling back to it. Our report
declared a custom theme and **no base theme at all** — nothing to fall back to.

The report now declares both, in the shape Desktop writes: the shipped `Fluent2-CY26SU08` base
theme as a `SharedResources` package, with `HelioExecutive.json` layered over it. The base theme
file in `src/powerbi_assets/` is Desktop's own, copied verbatim out of the project it wrote.

This was not the cause of the missing pages — the `.pbir` version fully accounts for that — but it
was a real defect in the same file, found by the same comparison.

### Desktop writes into a project it opens

Opening the project made Desktop add per-user state that must never be committed:

| Path | What it is |
|---|---|
| `.pbi/localSettings.json` | a machine-bound security-binding signature |
| `.pbi/cache.abf` | a local cache of the loaded model data |
| `.pbi/editorSettings.json` | editor state |
| `diagramLayout.json` | where tables sit in the model diagram |

It also stamped `RepoRoot` in `expressions.tmdl` with the absolute path of this clone — which is
precisely what the committed-empty-parameter rule exists to prevent, and what the
no-machine-paths check would have failed on. All of it is now in `.gitignore`, and two checks fail
the build if any of it reaches the repository.

**Regenerating is what makes the project committable again after a Desktop session.** Desktop's
save is not the source of truth; `src/build_powerbi.py` is.

### The guards

`check_report_pages` in `src/validate_powerbi.py`, 40 checks, driven by `DESKTOP_PBIR_CONTRACT` in
`src/build_powerbi.py` — the values Desktop reads, recorded as Desktop writes them:

- every contract value matches Desktop's own, `definition.pbir` `version` first among them
- `pageOrder`, the page folders and each `page.json` `name` form one bijection, in declared order
- `activePageName` names a real page; no page folder is orphaned out of `pageOrder`
- every page has a non-empty `displayName`, is not `HiddenInViewMode`, and is not typed `Tooltip`
  or `Drillthrough` — three further ways to produce the same "no pages" symptom
- every `visual.json` sits in its own folder under the page's `visuals/`, names itself after that
  folder, parses, and carries `name` and `position`
- the base theme is declared and packaged
- no Desktop-local state is committed

Five mutation tests prove they fail: `version` set back to `"1.0"`, a page dropped from
`pageOrder`, a page marked hidden, a `visual.json` renamed, and a `.pbi/localSettings.json`
planted. The first reproduces the exact failure — and, crucially, it is a project that Microsoft's
validator still passes.

## 16. Number, label and axis formatting

Desktop rendered the report and the numbers were unreadable: axes read `$0MM`, table cells read
`$4,781,152.1,,M` and `$853,381K`, chart labels read `$2.1,,MM`. Every underlying value was
correct. Two mechanisms were fighting each other.

**No DAX, no arithmetic, no mart and no layout changed in this pass.**

### The rule that was broken

A scaling comma in a number format is only honoured **at the end of a format section**. Followed
by a suffix — `#,##0.0,,"M"` — the tabular engine behind Power BI stops reading it as a scaler and
prints it. Excel is lenient about this; Power BI is not. So:

| Format | Value | Rendered |
|---|---|---|
| `\$#,##0.0,,"M"` | 4,781,152 | `$4,781,152.1,,M` |
| `\$#,##0,"K"` | 853,381 | `$853,381K` |
| `$#,##0.0,,""M""` (dynamic) | 6,000,000 | `$6,000,000.0,,M` |

Every format *without* a scaler had always rendered correctly — `23.5 mo`, `74.1%`, `534`, `0.43`
— which is what identified the pattern.

On charts a second fault compounded it. A visual's display units default to **Auto**, so Power BI
scaled the value by a million and appended `M`, then the format string tried to scale it again:
`$34.8M` became `$0MM`. Setting `labelDisplayUnits: 0` on the data labels had not helped, because
`0` means Auto — not "use the measure's format", as it had been read.

### The rule now

**A format string states the unit. A visual states the scale.** They are separate concerns and
Power BI has a mechanism for each; the failure came from trying to do both in the format string.

- **No format string scales or carries a currency suffix.** Currency is `\$#,##0;(\$#,##0);\$0`,
  signed currency `+\$#,##0;(\$#,##0);\$0`. Percentages, months, ratios, basis points and counts
  are unchanged — they never scaled, and they always worked.
- **Every chart states its display unit explicitly**, through `valueAxis.labelDisplayUnits` and
  `labelPrecision`, with `secLabelDisplayUnits` for a combo chart's second axis. Nothing is left
  on Auto, so nothing is scaled twice.
- **Data labels state the same unit as the axis they sit against**, so a label and its axis can
  never disagree.

| Visual | Axis | Renders |
|---|---|---|
| Exit ARR bridge, scenario ARR, forward ATR, H2 capacity, revenue, accounting panel | Millions, 1 dp | `$37.6M`, `$3.7M`, `$15.2M` |
| Operating income bridge | Millions, 1 dp axis / 2 dp labels | `$0.09M` on a $5.7M walk |
| ARR movement (primary), GTM constraint | Thousands, 0 dp | `$346K`, `$519K` |
| ARR movement (secondary), revenue margin (secondary) | Millions / None | `$34.8M`, `78.4%` |
| Retention trend, efficiency pair | None | `101.8%`, `0.43` |
| Policy runway, affordability | None, 1 dp | `24.0 mo` |

### What this costs, and why it is still right

A table column has no display-unit setting in a generated PBIR file — the per-column selector
shape is not documented in the published schema, and this project does not guess at PBIR shapes
any more (sections 12 to 15 are what guessing cost). **So table cells show full dollars**:
`$37,589,316`, `($2,793,686)`, `$4,781,152`.

That is unambiguous and correct, if less compact than `$37.6M`. Charts — where scale matters most
for reading a trend — carry proper units. If the executive tables should read `$37.6M`, the way to
get there is per-column display units in Desktop, saved back into the report; that is a Desktop
round-trip rather than a generator change, and it is the one open presentation item.

### The mixed-metric scorecard

One measure serves eleven metrics in four units, so its format is chosen per row from the mart's
own `Unit` column. Three things were wrong and are fixed:

- the currency branch tried to scale, and printed `$6,000,000.0,,M`. It no longer scales.
- **gross margin is stored in basis points**, so the levels read `7,407 bps` where a level should
  read `74.1%`. No format string can bridge that — a scaling comma divides by 1,000 and `%`
  multiplies by 100, and there is no divide-by-100 token — so the two level measures express the
  basis-point rows as a ratio and format them `0.0%`. **A change of unit, not of quantity**: 7,406.9
  bps and 0.74069 are the same margin, the mart is untouched, and the variance keeps its stored
  basis points.
- a **Total row** summed dollars, basis points and headcount together.

Every row, as it now reads:

| Metric | Budget | Base | Variance |
|---|---|---|---|
| Ending Headcount | 214.0 | 217.7 | +3.7 |
| Gross Margin | 74.1% | 78.4% | +429 bps |
| New Logo ARR | $6,000,000 | $3,206,314 | ($2,793,686) |
| Exit ARR | $37,589,316 | $34,816,417 | ($2,772,899) |
| Operating Income / (Loss) | ($5,625,467) | ($5,713,689) | ($88,222) |

Variance % is one decimal throughout: `-46.6%`, `-7.4%`, `+6.2%`. Levels are unsigned with
accounting parentheses; the variance is signed in every unit. A dollar sign may appear only on the
`usd` branch. Neither measure uses `FORMAT()`, which would return text and break sorting.

### The total row

A total over rows that are *different metrics* is arithmetic nonsense. It is off on the four
tables whose rows are incommensurable: both Budget-vs-Base scorecards, the executive KPI band (a
single row, where a total duplicates it) and the scenario assumptions matrix.

Totals stay **on** everywhere else, deliberately. Power BI recomputes a measure in the total row's
filter context rather than summing what is on screen, so a total over segments gives a correctly
blended NRR and a total over P&L line items gives the company figure.

### Data labels

Off by default in the theme, which is right for a 24-to-48 month line: a label on every point is
unreadable and the tooltip carries the exact value. On for six discrete-column visuals — the two
waterfalls, H2 capacity versus pipeline, forward ATR, and the two runway charts.

### What the checks catch

Seventeen checks in `check_measure_presentation`. They cannot prove how Power BI renders, but they
catch every mismatch that made a correct number unreadable:

- **no format string scales** — the defect itself
- every visible measure uses one of the fourteen declared formats
- **every chart states its axis display unit**, and none is left on Auto — the double-scaling
- **every data label states the same unit as its axis**
- no format mixes a percent sign with a currency scale; no chart axis mixes unit kinds
- data labels only where intended, and never on a line chart
- the scorecard's dynamic format covers every unit its mart carries, keeps dollars on the dollar
  branch, and does not try to scale
- no mixed-metric table shows a total row

## 17. Visual QA against the rendered report

With the project opening, refreshing and rendering, the five pages were read as a reader sees
them. The palette, header system, conclusion-led titles and page flow held up. What did not was
density: a KPI band showing its headers and a scrollbar but none of its values, nine tables
scrolling sideways, an accounting panel replaced by a placeholder icon, a Board floor drawn as a
second bar, and totals summing scenarios that cannot coexist.

**No layout was redesigned and no calculation changed.** Every fix is density, formatting or a
totals setting.

### The subtitle nobody asked for

Power BI writes its own subtitle from the field names — *"Deferred Revenue, Unbilled Receivable
and Capitali…"*, *"Policy Runway Months and Board Floor…"*. It appeared on every visual, repeated
what the title already said, truncated, and took a line of plot area with it. It is now off in
the theme, which fixed every truncated subtitle in the pack at once.

### The panel that would not render

`p4v5_accounting_panel` showed Desktop's placeholder icon. Not a binding fault and not a schema
fault: at 152px, once a two-line title and that auto-subtitle had taken their share, there was no
plot area left, and Desktop substitutes an icon rather than draw nothing. Removing the subtitle
and giving it 186px fixed it. A check now fails any chart under 140px.

### What changed

| Area | Change |
|---|---|
| **Columns** | Nine tables trimmed — the KPI band 10 → 8, the two scorecards 6 → 5, GTM KPIs 8 → 6, the pipeline band 10 → 4, headcount 5 → 4, and four others. Every table now has at least 81px per column |
| **Totals** | Off on the hiring-case table and both runway tables. Hiring cases and runway paths are **alternatives**; a total added scenarios that never coexist |
| **Board floor** | No longer a second series. A dashed amber reference line at 24 months, labelled — the threshold a bar clears or does not |
| **Zero labels** | Bridge steps and forward ATR use a format whose empty third section renders zero as blank, so `$0.00M` and rows of `$0.0M` are gone |
| **Axis units** | The ARR movement axis moved from Thousands to Millions: `$2,000K` beside a `$40.0M` secondary axis read as two different reports |
| **Ratios** | Sales efficiency and the Magic Number read `0.43x`, not `0.43` |
| **Bridge labels** | A short `Bridge Step` label for the category axis. *"Opening ARR variance (31-Dec-2025 actual, identical both sides)"* wrapped to three truncated lines; the full wording stays on the hidden stored column |
| **Geometry** | Page 1 rebalanced for the taller band; the accounting panel and the page-5 runway chart given room |
| **Matrix** | The assumptions matrix renders flat — stepped layout and `[+]` toggles off for what is a flat driver list |

### Nineteen measures the pages no longer show

Cutting columns orphaned nineteen measures. They are **kept, not deleted**: each is documented in
`measures.md`, several are exercised by the SQL-to-DAX pack, and a reader who opens the model
should find the obvious companion metric — Beginning ARR beside the flows, the percentage twin of
a variance, the GTM diagnostics behind the page's conclusion.

They are declared in `MODEL_ONLY_MEASURES` with a reason, and two checks keep the list honest: no
measure on a page may claim the exemption, and anything new that stops being read still fails.
The restraint rule keeps its teeth; what changed is that the model now carries a slightly richer
surface than the five pages display, and says so.

### What the checks catch

`check_visual_density`, 16 checks: columns against width, charts against a minimum height, no
overlap, nothing off canvas, the auto-subtitle off, no title long enough to wrap past two lines,
no total on a table of alternatives, the Board floor as a reference line, and the model-only list
staying honest. Three mutation tests prove them: an overcrowded table, a chart too small to
render, and a restored scenario total.

These are arithmetic — fields against pixels — not proof of how Desktop lays anything out. The
screenshots remain the authority.

## 18. Deviations from PHASE1_SPEC section 12

Recorded rather than left silent, following the convention `docs/gtm_finance.md` and
`docs/excel_operating_model.md` use.

1. **No benchmarks anywhere.** Section 4 gives the reason in full. The spec's benchmark columns
   are therefore empty on every page.
2. **The scorecards carry no prior-year column.** The spec asks for actual / budget / reforecast /
   prior year on pages 1 and 4. The page 4 P&L does show prior year — it pivots on Fiscal Year, so
   FY2025 sits beside FY2026 — but the two Budget-versus-Base scorecards do not, because
   `fct_management_variance` carries only the Budget and Base amounts the Phase 7 layer computes
   and controls. Assembling a prior-year column here from a different mart at a different grain
   would put an uncontrolled number on a board page.
3. **Rep attainment distribution, top churn and expansion accounts, and open reqs / slippage are
   not shown.** Six analytical visuals per page is a hard ceiling in the same spec section, and
   these lost to the visuals that answer the eight management questions directly. The underlying
   marts exist; the visuals do not.
4. **Customer concentration appears as a measure, not a visual** (`Top 10 ARR Concentration
   (Jun-26)`), for the same reason.

## 19. Limitations

1. **Desktop acceptance was reached only after five rounds of defects.** Sections 11 to 16. Every
   one passed static validation and still reached Desktop broken, which is the proof that no static
   check substitutes for opening the file. Any future change to the report or the model needs the
   same manual pass before the captures can be trusted.
2. **`visual.json`'s schema version is still inferred, not confirmed.** The Desktop-authored
   scaffold that section 15 finally provided is a *blank* report — Desktop wrote it after
   discarding ours — so it contains no visuals and still cannot settle the visual container
   version. `visualContainer/2.9.0` is the highest published version, is consistent with the
   `2.0.0` report definition version, and validates against Microsoft's own validator, but it is
   the one part of the contract never read off a Desktop-authored file. A Desktop `.pbip` **with
   at least one visual on a page** would settle it.
3. **Desktop normalises the TMDL it saves.** It drops properties that hold their default
   (`crossFilteringBehavior: oneDirection`), unquotes identifiers it considers bare-safe, and adds
   a trailing newline. Those are cosmetic and change nothing semantic — Desktop altered no
   measure, column, format string, relationship or partition — but a Desktop save will show a diff
   against the generated project. Regenerate before committing; see section 7.
4. **The report is a read layer.** It cannot change a driver and re-forecast. Changing an
   assumption means editing `config/assumptions.yml` and rebuilding the analytical layer — the
   assumptions stay version-controlled rather than buried in a report.
5. **Import mode over local CSVs.** There is no gateway, no workspace and no scheduled refresh.
   Refresh means "re-read the committed marts on this machine". Publishing to the Power BI Service
   would need a data source those services can reach, and that is out of scope.
6. **The RepoRoot parameter must be set after cloning.** A deliberate cost of not committing an
   absolute path. The first refresh on a fresh clone fails until it is set.
7. **Eight tables are disconnected from the calendar.** Section 5 gives each reason. The practical
   consequence: a date filter does not change those visuals, which is correct but can look
   surprising until the reason is read.
8. **The GTM constraint mart carries forecast months only**, so actual months show blank capacity
   by design. The page says so rather than plotting a zero.
9. **Deferred revenue and billings are actual periods only.** The contract billing schedule stops
   at the reporting date; no forecast billings series is invented.
10. **The commission asset is analytically derived, not GL-reconciled.** `fact_gl_actuals` is a P&L
   extract with no balance sheet — the same limitation Phase 8 records.
11. **Mart exports are not byte-stable across rebuilds.** `src/run_sql.py` orders each export by
    its first two columns, so ties can reorder and DuckDB's parallel aggregation moves the last
    digit or two of some floats. This predates Phase 10 and affects the CSVs, not the project: the
    expected-results pack is regenerated from the marts in the same build, and the tolerances in
    section 11 are far wider than that dust.
12. **Segment-level Budget ARR figures are allocations.** `fact_budget` carries no segment grain for
    ARR movements, so the Budget side of any segment ARR bridge is allocated and labelled as such
    upstream. Base's segment figures are always segment-native.
13. **No mobile layout.** The pages are authored at 1280×720 for a board screen.
